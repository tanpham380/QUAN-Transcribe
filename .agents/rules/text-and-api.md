# Text output and API shape rules

## Post-processing is a pipeline with a fixed order

`PostProcessor.process` runs, in order:

1. Normalization — either ITN (`inverse_text_normalization`) or TN
   (`text_normalization` via sea-g2p), selected by `norm_mode`.
2. Capitalization (`capitalize_vietnamese`).
3. Punctuation (`punctuate_vietnamese`).

Order matters: ITN produces digits and symbols that capitalization and
punctuation then treat as ordinary text. Do not reorder without a reason.

## The raw model output

QUAN-Transcribe's raw CTC output is **lowercase Vietnamese without punctuation**,
with numbers spelled out as words:

- `"xin chào tôi tên là nam"`
- `"năm mươi phần trăm"`

The model has no language-conditioning input, so `vi` / `vietnamese` are the
only accepted language values (`SUPPORTED_LANGUAGES` in `app/config.py`).

## Known limits of the current implementation

Be honest about these when touching the module — they are the reason the
implementation is a candidate for replacement:

- **Capitalization** relies on a hardcoded dict of ~30 place names and ~23
  acronyms, plus a regex for sentence starts. Anything outside the dict stays
  lowercase.
- **Punctuation** is regex question-word detection (`phải không`, `ai`, `gì`,
  `ở đâu`, ...) and appends `.` or `?`. It cannot place commas or colons, and it
  only punctuates the end of a segment.
- **ITN** is six sequential regex passes over Vietnamese number words. It handles
  dates, years, percentages, currency, decimals and compound numbers, but the
  passes can interact and the year heuristic (`1900 <= val <= 2100`) is a
  disambiguation hack.

If you improve one of these, keep the existing function signatures and the
`PostProcessor` flags (`enable_punctuation`, `enable_itn`,
`enable_capitalization`, `enable_g2p`, `norm_mode`) so callers do not break.

## `is_final` matters

`punctuate_vietnamese(text, is_final=...)` only appends terminal punctuation when
`is_final` is true. Streaming partials must not get a trailing `.` that then
disappears. `process_segments` passes `is_final=True` only for the last segment.

## Response formats

`app/formats.py` renders `json`, `text`, `srt`, `verbose_json` and `vtt`.
`merge_segments_by_sentence` joins adjacent pieces whose boundary is not a real
pause — the model splits on energy, not semantics, so a 90 s file can become
three pieces with a mid-sentence boundary. A boundary is real when the previous
text ends in `.?!…:;` **or** the gap is ≥ 0.5 s.

## Request parsing

`app/schemas.py` parses `multipart/form-data` by hand because there is no
Pydantic model for it. Unknown fields are **ignored**, not rejected, matching how
OpenAI's API tolerates extra fields. Server-side bounds (`MIN_CHUNK_SECONDS`,
`MAX_CHUNK_SECONDS`, `MAX_BEAM_WIDTH`) exist so a stray field cannot make the
model do unbounded work — keep them.

Errors must render in OpenAI's envelope via `APIError.to_payload()`.

## Never

- Hand-edit `app/proto/*_pb2*.py` — generated by `protoc`.
- Change the error envelope shape; OpenAI clients depend on it.
